

# Floran Krnel Docker 支持 — 完整排查与填坑复盘

**设备**: OnePlus Ace 3 Pro (OP5D06L1)

**ROM**: crDroid 16 (Android 15) 

**内核**: GKI 6.1 (Floran-Kernel, ReSukiSU + SUSFS) 

> **前言** 在给 OnePlus Ace 3 Pro 适配 Docker 的过程中，可以说是踩满了各种冷门坑。最开始通过 `check-config.sh` 发现内核大量配置缺失，盲目补齐全部 Docker/VM 特性后直接导致了 **Bootloop**。通过二分法排查，最终剔除了冗余的 cgroup v1 遗留项（如 `CGROUP_DEVICE`、`CGROUP_PIDS` 等）、`BTRFS_FS` 以及多余的 patch，收敛出一套精简安全的配置（保留 `NAMESPACES`、`SECCOMP`、`VETH`、`NF_TABLES` 等），让 Docker 在 `vfs` 驱动下成功跑起来。
>
> 但这只是个开始，接踵而至的是开机 375 秒卡死、电池失效、以及 Loop 挂载 `I/O error`。以下是整个问题的排查全景与填坑记录。

## 一、问题全景速查

| #    | 问题现象                       | 根因简述                                              | 最终状态                        |
| ---- | ------------------------------ | ----------------------------------------------------- | ------------------------------- |
| 1    | 内核 Docker 配置导致 Bootloop  | 引入不兼容的 cgroup v1 遗留项与调度策略               | ✅ 已修复（收敛最小配置集）      |
| 2    | 开机时间飙升至 375 秒          | AOSP `restorecon` 递归扫描 Docker VFS 的 174 万个文件 | ✅ 已修复（改用 Loop ext4 镜像） |

| 4    | Loop 挂载触发 `I/O error`      | F2FS 垃圾回收机制与稀疏文件的物理块分配冲突           | ✅ 已修复（转为非稀疏镜像）      |

## 二、开机 375 秒的元凶：AOSP `restorecon` 与 VFS 碎片

### 2.1 现象与取证

刷入 [mgksu/dockerd](https://github.com/mgksu/dockerd) 模块后，系统冷启动耗时直接从正常的十几秒飙升到 **375 秒**。

通过串行捕获早期 `dmesg`，在 t \approx 380\text{s} 处抓到了关键日志：

```
[398.835][T1] selinux: Could not set context for /data/adb/docker/lib/docker/image/vfs/...
[398.876][T1] selinux: Could not stat /data/adb/docker/run/docker.sock: Permission denied
```

以及 AOSP init 的关键耗时输出：

```
t+380.3s [T1] init: Command 'restorecon --recursive --skip-ce /data'
              action=post-fs-data (/system/etc/init/hw/init.rc:1074)
              took 375256ms and succeeded
```

**根本原因**: AOSP 的 `init` 进程在 `post-fs-data` 阶段会执行 `restorecon -R /data` 进行 SELinux 标签递归重标注。由于 Docker 的 VFS 存储驱动在宿主机生成了高达 **174 万个独立小文件**（总体积 41GB），每次开机 `restorecon` 都要对这 174 万个文件逐个尝试 `setfilecon` 并刷写大量的 audit 日志，纯粹的 I/O 开销直接把开机卡死。

### 2.2 解决方案：Loop Ext4 镜像封装

把 Docker 的 `data-root` 整体收纳进一个环回（Loop）Ext4 镜像文件中。这样对 AOSP 的 `init` 来说，整个目录变成了一个静态的镜像文件，彻底避开了海量碎文件的递归重标注。

```bash
# 创建 50G 专属镜像
dd if=/dev/zero of=/data/adb/docker-data.img bs=1M count=51200
mkfs.ext4 /data/adb/docker-data.img

# 挂载（显式指定 SELinux Context 绕过动态扫描开销）
DEV=$(losetup -f)
losetup $DEV /data/adb/docker-data.img
mount -t ext4 -o "context=\"u:object_r:adb_data_file:s0\"" \
    $DEV /data/adb/docker/lib/docker
```

**效果**: 开机耗时从 375s 直接压降至 **40s**。

## 三、电池检测失败的次生灾害

开机后执行 `dumpsys battery` 发现返回 `present: false, level: 0`。 排查发现这和 375 秒卡死是**同一个病根**——由于早期开机卡在 `restorecon` 阶段过久，底层充电驱动 (`OPLUS_CHG` / `MMS_GAUGE`) 在初始化生命周期内超时耗尽，注册失败。当开机提速到 40s 后，电源管理栈恢复正常，电池状态自动恢复为 `present=1, level=100`。

## 四、F2FS 稀疏文件与 Loop 驱动不兼容 (I/O error)

### 4.1 现象

系统重启后，Docker 修复模块挂载失败，内核环形缓冲区报错：

```
I/O error, dev loop42, sector 2
EXT4-fs (loop42): unable to read superblock
```

### 4.2 排查与根因

经过交叉测试确认：小镜像挂载正常、直接用 `dd` 读镜像也正常，唯独 **50G 的稀疏镜像（Sparse File）通过 Loop 挂载时会稳定触发 `I/O error`**。

**底层机理**: 移动端主流的 **F2FS 文件系统**，其垃圾回收（GC）和动态块分配（Extents/Holes）机制，与内核 Loop 块设备驱动在处理大容量稀疏文件“空洞”时的读取路径存在冲突。用户态直接读文件时 F2FS 会透明处理空洞，但当 Loop 驱动通过块设备接口进行底层随机寻址时，无法正确解析复杂的间接物理块映射，导致读取崩掉。

### 4.3 解决办法

放弃稀疏文件，做物理空间全量预分配：

```bash
# 检查是否为稀疏文件（actual < apparent）
blocks=$(stat -c %b $IMG); blocksize=$(stat -c %B $IMG)
actual=$((blocks * blocksize)); apparent=$(stat -c %s $IMG)

# 转换形态（填充空洞）
cp $IMG ${IMG}.nosparse && mv ${IMG}.nosparse $IMG
```

*(注：以后初始化镜像直接用标准的 `dd if=/dev/zero`，切勿用 `seek` 挖空洞)*

## 五、模块封装与避坑指南

### 5.1 `docker-fix` 模块设计

编写了自动化管理脚本：

- `action.sh`: KernelSU 图形化一键修复（清理 stale loop -> 绑定设备 -> 启动 dockerd -> 冒烟测试）。
- `service.sh`: `boot_completed` 触发态守护（带 10 轮重试）。
- `post-fs-data.sh`: 早期文件系统初始化阶段的快速挂载尝试。

### 5.2 避坑：Loop 设备次设备号（Minor）计算

当内核启用 `loop.max_part=7` 时，每个 Loop 设备的次设备号是以 **8** 为步进的（例如 `loop42` 对应 minor `336`）。

- ⚠️ **严禁**手动 `mknod /dev/block/loopN b 7 N` 创建节点，会导致严重的设备号错位。
- 正确做法：全部交由 `losetup -f` 动态检索并自动建立。
