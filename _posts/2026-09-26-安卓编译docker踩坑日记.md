
# 在 OnePlus Ace 3 Pro (sm8650) 上跑通 Docker：一个 GKI 内核的 bootloop 血泪史与用户态四连坑

> **设备**：OnePlus Ace 3 Pro（`pineapple` / SM8650，Snapdragon 8 Gen 3）· crDroid 16 (Android 15) · GKI 6.1 内核 · ReSukiSU (KernelSU fork) + SUSFS
>
> **TL;DR**：内核层搞定能开机的 Docker 版（FD）→ Termux 方案被非 PIE runc 判死刑 → 换 KernelSU 模块 `mgksu/dockerd` + 踩坑修改 4 处配置 → 顺利输出 `Hello from Docker!`。同一条工作流里的 VM/KVM 开关也单独跑了一遍，**能开机，但 SM8650 的 EL2 被占用，无法真正做 KVM 宿主**。

## 0. 为什么要自己折腾

GKI 通用内核出于启动兼容性考虑，裁掉了大量 Docker 依赖的 CONFIG。如果直接在 crDroid 内核源码上暴力开齐 Docker 选项，迎接你的大概率是一场无限 **bootloop**。

要把这件事做成，本质上要打赢三场战争：

1. **内核层**：揪出导致 bootloop 的元凶 config，果断砍掉换取成功开机；
2. **用户态层（Termux）**：即使内核配齐，用户态依然满地是坑；
3. **模块层**：引入自带完整用户态的 KernelSU 模块，做最后的收尾与跑通。

## 1. 内核层：用二分法把 bootloop 元凶钉死

### 1.1 构建环境

基于 GitHub Actions 自动构建工作流仓库 [greenhandzdl/Floran-Kernel](https://github.com/greenhandzdl/Floran-Kernel?utm_source=gemini)（上游：[AkiHaza/Floran-Kernel](https://github.com/AkiHaza/Floran-Kernel?utm_source=gemini)），内核源码采用 [crdroidandroid/android_kernel_oneplus_sm8650](https://github.com/crdroidandroid/android_kernel_oneplus_sm8650?utm_source=gemini)（`16.0` 分支）。

开启 `Enable Docker Container Support` 后，构建流程会将 [`patch/docker.config`](https://github.com/greenhandzdl/Floran-Kernel/blob/main/patch/docker.config?utm_source=gemini) 追加到 `arch/arm64/configs/gki_defconfig` 中，以补全 [moby check-config.sh](https://github.com/moby/moby/blob/master/contrib/check-config.sh?utm_source=gemini) 提示的缺失项。

### 1.2 踩坑与排查

**整簇开启 = 毫无日志的死机**

首次尝试刷入全量 Docker config，手机直接卡在 RGB 灯循环重启。GKI 设备在 bootloop 时极难获取 dmesg（无串口、RAMOOPS 也不可靠），只能靠**刷机矩阵 + 单变量控制**强行排查。

做法很简单：每次只改动一个变量。我将 `docker.config` 拆分成若干功能簇（cgroup 簇、网络簇、sched 簇、overlay 簇等），拉上 Baseline 挨个测试：

| **实验**                     | **测试内容**           | **结果**                   |
| ---------------------------- | ---------------------- | -------------------------- |
| Baseline                     | 原版 docker.config     | ✅ 正常开机                 |
| A / D / E / H / K1 / K3 / FN | 开启各子功能簇         | ❌ bootloop                 |
| C / F / K2                   | 开启各子功能簇         | ✅ 正常开机                 |
| **FD**                       | 底座 + USER_NS + BTRFS | ✅ 正常开机（最终交付形态） |

**元凶一：`CONFIG_CFS_BANDWIDTH`**

单变量测试很快锁定了问题：只要开启 `CFS_BANDWIDTH`（配合 `FAIR_GROUP_SCHED`/`CGROUP_SCHED` 实现容器 CPU 限制），系统必崩。

根因在于它**改变了调度器相关结构体的内存布局**。当 Vendor 预编译模块（`.ko` 强依赖 GKI KMI 校验）加载时，结构体偏移量对不上，直接引发内核早期崩溃。这类“改个 config 导致 ABI 突变”的深坑，在编译期没有任何 Warning。

**元凶二：`docker_net` 网络簇**

包括 `br_netfilter`、`veth`、`bridge netfilter`、`XT_MATCH_ADDRTYPE` 等。

这部分在 Vendor 配置里本来是 `=m`（模块化），但 Docker 通常要求编译为 `=y`（内建）。**这种 `=m` 到 `=y` 的转变本身就是对 KMI 的破坏**，会导致 Vendor 模块符号版本匹配失败。彻底砍掉这一整簇后开机恢复正常，代价很明确：**这台设备无法创建 `docker0` 网桥，也无法直接写入 iptables NAT 规则**。

**调试心得**

1. **单变量对照 > 读代码瞎猜**。在 GKI 的环境下，各种 config 叠加带来的副作用很难做静态分析；
2. **永远以 runtime 为准**。能进系统时直接检查 `/proc/config.gz`，比看源码里的 `defconfig` 靠谱得多——补丁打失败往往是静默的；
3. 在 CI 工作流里，如果 `git apply` 后面带了 `|| true`，补丁即便失败也不会触发构建中断。产物看起来一切正常，实际根本没打进去，务必检查运行时配置。

### 1.3 交付形态（FD）

最终的配方为：`FD = docker.config 底座 + NAMESPACES/USER_NS + BTRFS`，验证 Tag：

[Crdroid-ReSukiSU-susfs-260926110344](https://github.com/greenhandzdl/Floran-Kernel/releases/tag/Crdroid-ReSukiSU-susfs-260926110344?utm_source=gemini)

**主动放弃的特性**：

- CFS 带宽限制（容器无法使用 `--cpus` 硬限额）；
- bridge / docker0 / iptables NAT（容器只能走 `--network=host`）。

这是为了能成功开机所做出的必要权衡。换来的是：系统稳定启动、命名空间完整、cgroup v2 可用。

## 2. Termux 层：内核搞定了，守护进程依然挂掉

刷入 FD 内核后，首先尝试在 Termux 里直接启动 `dockerd`，很快发现内核通关只是第一步，用户态的坑才刚刚开始。

### 2.1 连环坑排查

**配置冲突导致拒启**

在 `daemon.json` 里配置了 `storage-driver`，同时命令行启动时又传入了 `-s overlay2`：

```
the following directives are specified both as a flag and in the configuration file: storage-driver
```

Docker 遇到了重复定义会直接退出。**处理方式**：统一收拢到 `daemon.json` 中，命令行保持干净。

**Android `/data` 分区与 overlay2 的冲突**

```
level=error msg="failed to mount overlay: invalid argument" storage-driver=overlay2
failed to start daemon: error initializing graphdriver: driver not supported: overlay2
```

第一反应以为是内核没编译 `OVERLAY_FS`——其实并不是，GKI 本身自带了 overlay 支持。真正的根因是 `/data` 分区采用了 **f2fs 并强制启用了 SELinux**，内核不会放行 `trusted.overlay.*` 扩展属性（xattr），导致 `mount` 操作统一返回 `EINVAL`。

这不是改改内核 config 就能解决的问题，而是 Android 文件系统栈的底色。**解法**：降级到 `vfs`（按层全量解包，虽然慢且占空间，但绝对稳妥）；后续也可以考虑使用 `fuse-overlayfs`（走用户态 + `user.*` xattr）。

Termux 方案的“死刑判决”：非 PIE 的 runc

将存储驱动换成 `vfs` 后，`dockerd` 终于成功启动，然而运行 `docker run hello-world` 时直接爆错：

```
OCI runtime create failed: ... unable to retrieve OCI runtime error log.json: no such file or directory
runc did not terminate successfully: exit status 1: unknown
```

提示信息被封装得毫无线索。**开启 `dockerd --debug` 重新排查**，终于在 Debug 日志深处看到了真正的原因：

```
"/data/data/com.termux/files/usr/bin/runc" has unexpected e_type: 2
```

`e_type=2` 代表 `ET_EXEC`，即**非 PIE 可执行文件**。runc 1.x 的 re-exec 机制要求二进制必须是 `ET_DYN`（PIE）。用 `readelf -h runc | grep Type` 验证，出来的确实是 `EXEC`。Termux 官方仓库打包的就是非 PIE 版本，哪怕重新安装结果也一样，而且仓库里也没有 `crun` 可以替代。

这属于用户态构建产物的问题，和内核没有任何关系，刷什么内核都无法绕过。Termux 方案到此宣告放弃。

*(注：Termux 自带的 docker 启动脚本还会尝试硬挂载一堆 cgroup v1 控制器并报 `Invalid argument`，是因为设备采用了 hybrid cgroup 布局。这些只是日志干扰，不需要去理会。)*

## 3. 模块层：接入 mgksu/dockerd 彻底跑通

最后引入现成的 KernelSU/Magisk 模块 **[mgksu/dockerd](https://github.com/mgksu/dockerd?utm_source=gemini)**。该模块将完整的用户态工具链（dockerd / containerd / **正规 PIE runc** / compose / buildx）打包释放到 `/data/adb/docker/bin` 并提供开机自启，逻辑参考了经典 Gist [FreddieOliveira/docker-on-android](https://gist.github.com/FreddieOliveira/efe850df7ff3951cb62d74bd770dce27?utm_source=gemini)。

### 3.1 环境变量配置

安装模块后，直接执行 `dockerd.service restart` 会提示 `command not found`。原因是控制脚本存放在 `/data/adb/docker/scripts/`（以及模块的 `system/bin/`）下，未打入默认 PATH。手动执行一次 `export PATH=/data/adb/docker/scripts:$PATH` 即可。开机自启则由 `/data/adb/service.d/dockerd_service.sh` 妥善接管。

### 3.2 解决 overlay2 问题

模块默认的 daemon 依然会报 `failed to mount overlay: invalid argument`。编辑 `/data/adb/docker/etc/docker/daemon.json`，将驱动强行修改为 `vfs`。

### 3.3 补全网络配置

解决存储驱动后，启动日志又卡在了网络初始化阶段：

```
failed to register "bridge" driver: failed to add jump rules to ipv4 NAT table:
iptables ... -m addrtype ...: Warning: Extension addrtype revision 0 not supported, missing kernel module?
iptables: No chain/target/match by that name.
```

这正是此前为了保证内核能够开机而**主动裁剪掉的 `docker_net` 网络簇**（`BRIDGE_NF` / `XT_MATCH_ADDRTYPE` 等）。既然内核层去掉了网络支持，就需要在用户态配置里关闭对应的网络行为。

在 `daemon.json` 中明确禁掉网桥与 iptables：

JSON

```
"bridge": "none",
"iptables": false,
"ip6tables": false
```

这意味着后续所有容器都需要使用 `--network=host` 模式运行。

### 3.4 配置镜像加速

解决上述问题后，执行 `docker run hello-world` 遇到镜像拉取超时：

```
Get "https://registry-1.docker.io/v2/": net/http: request canceled while waiting for connection
```

在国内直连 Docker Hub 经常超时，在 `daemon.json` 中补充 Mirror 节点配置：

JSON

```
"registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://docker.1ms.run",
    "https://docker.xuanyuan.me"
]
```

### 3.5 完整 daemon.json 配置文件

最终配置文件 `/data/adb/docker/etc/docker/daemon.json` 内容如下：

JSON

```
{
    "data-root": "/data/adb/docker/lib/docker",
    "exec-root": "/data/adb/docker/run/docker",
    "pidfile": "/data/adb/docker/run/docker.pid",
    "init-path": "/data/adb/docker/bin/docker-init",
    "userland-proxy-path": "/data/adb/docker/bin/docker-proxy",
    "hosts": ["unix:///data/adb/docker/run/docker.sock"],
    "storage-driver": "vfs",
    "bridge": "none",
    "iptables": false,
    "ip6tables": false,
    "registry-mirrors": ["https://docker.m.daocloud.io", "https://docker.1ms.run", "https://docker.xuanyuan.me"]
}
```

保存配置后重启服务：`dockerd.service restart && sleep 6`。

测试运行：

Bash

```
# docker run --rm --network=host hello-world
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
...
Hello from Docker!
```

通过 `docker run -it --rm --network=host ubuntu bash` 进入容器交互正常。日常使用建议在 Shell 配置文件中设置好环境变量（将 PATH 指向 `/data/adb/docker/bin`，并指定 `DOCKER_HOST=unix:///data/adb/docker/run/docker.sock`）。

## 4. 最终状态与能力边界

| **功能**                             | **运行状态** | **说明**                                                    |
| ------------------------------------ | ------------ | ----------------------------------------------------------- |
| 容器基础运行 (runc / ns / cgroup v2) | ✅ 正常       | 基础容器功能全链路打通                                      |
| docker compose 编排                  | ✅ 正常       | 需使用 `network_mode: "host"`，服务间走 localhost 通信      |
| Port 映射 / 自定义 bridge 网络       | ❌ 不可用     | 内核网络簇为解决 bootloop 已裁剪                            |
| `--cpus` 硬限制                      | ❌ 不可用     | `CFS_BANDWIDTH` 会引发 bootloop                             |
| rootless / userns-remap              | ✅ 正常       | 保留了 `USER_NS`                                            |
| 守护进程开机自启                     | ✅ 正常       | 依赖模块 `service.d` 脚本                                   |
| 存储驱动性能                         | ⚠️ 一般       | `vfs` 按层解包性能较差且占空间，后期可尝试 `fuse-overlayfs` |
| KVM 虚拟化 (QEMU-KVM / firecracker)  | ❌ 不可用     | 内核编译通过，但硬件 EL2 被占用，无 `/dev/kvm` 设备         |

## 5. 踩坑小结

1. **GKI 配置变更风险极高**：类似 `CFS_BANDWIDTH` 这种改动会破坏结构体布局，而 `=m` 转 `=y` 则会破坏 Vendor KMI，两者均会导致静默的 bootloop，且没有任何编译提示；
2. **排查 Bootloop 依赖矩阵测试**：每次只调整一个变量，静态分析在 GKI 的组合效应面前效果有限；
3. **警惕 CI 构建静默失败**：`git apply ... || true` 会掩盖补丁失效，产物需通过 `/proc/config.gz` 进行运行时抽查；
4. **`/data` 分区不支持 overlay2**：由于 f2fs 与 SELinux 对 trusted xattr 的限制，Android `/data` 上使用 overlay2 必挂，`vfs` 是通用的保底方案；
5. **善用 Debug 日志**：遇到 `log.json no such file` 等模棱两可的错误时，开启 `--debug` 能直接暴露非 PIE runc 等底层根因；
6. **关注逻辑对应关系**：内核层裁掉了什么功能（如 bridge/iptables），用户态配置中就要同步禁用，避免守护进程调用不存在的内核模块。

## 6. 补充验证：VM / KVM 虚拟化

在同一个构建体系中，还包含一个与 Docker 平级的 `vm` 开关。开启后会将 [`patch/vm.config`](https://github.com/greenhandzdl/Floran-Kernel/blob/main/patch/vm.config?utm_source=gemini) 追加至 `gki_defconfig`，包含 KVM 宿主（`CONFIG_KVM`/`CONFIG_HAVE_KVM`）、网络（`TUN`/`TAP`/`VHOST`/`VHOST_NET`）、virtio 组件及 `9P_FS` 支持。

**测试结果**：

- **系统能够正常启动**：单独开启 `vm=true`（Tag [Crdroid-ReSukiSU-susfs-260926111316](https://github.com/greenhandzdl/Floran-Kernel/releases/tag/Crdroid-ReSukiSU-susfs-260926111316?utm_source=gemini)）未触发 bootloop，说明开启 `CONFIG_KVM=y` 及相关内建模块在此设备上没有破坏 Vendor KMI。

- **但 KVM 宿主无法使用**：解压 `/proc/config.gz` 可以看到 `CONFIG_KVM=y` 已生效，但系统中并未生成 `/dev/kvm` 节点。检查内核设备清单：

  Bash

  ```
  cat /proc/misc | grep -i kvm      # 无输出
  dmesg | grep -iE 'kvm|hyp|el2'    # 无输出
  ```

  清单为空意味着内核并未成功注册该设备。

**原因分析**：

arm64 架构下的 KVM 宿主需要运行在 **EL2 异常级**。在 SM8650 平台上，高通预装的 EL2 Monitor（pKVM / Secure Hypervisor）在启动时已经占用了 EL2，Android Linux 内核仅作为 **EL1 Guest** 运行。在没有 EL2 权限的情况下，内核 `kvm_init` 中的 `has_hyp_mode()` 检查失败，因此静默放弃了 `/dev/kvm` 的注册。

**结论**：在当前硬件与固件限制下，该配置仅能提供 `TUN/TAP/vhost/virtio` 等宿主侧支持（适用于纯软件模拟的 QEMU TCG 或特定网络工具），**无法进行硬件加速的虚拟化**。

### 6.1 全功能组合包验证 (docker + vm + droidspaces=extended)

尝试将三者合并构建（Tag [Crdroid-ReSukiSU-susfs-260926123027](https://github.com/greenhandzdl/Floran-Kernel/releases/tag/Crdroid-ReSukiSU-susfs-260926123027?utm_source=gemini)，产物 `Crdroid-ReSukiSU-SUSFS-dss-ext-docker-vm-0926.zip`），实测表现为：**系统正常启动、ReSukiSU + SUSFS 正常、Docker 全链路测试通过**；VM 部分依然受限于 EL2 占用。多种配置叠加未引入新的冲突或 bootloop。
