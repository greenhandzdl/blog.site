# 折腾 Marvis 等 GUI 程序找不到 Homebrew PATH 的排查与优雅解法

> **一句话总结**：Marvis（腾讯 macOS 端 AI 助手）或其他通过 LaunchAgent / `open` 命令启动的 GUI 应用，在内部执行 shell 命令或拉起 npx 类 MCP 服务器时，经常报 `command not found: npx` 或 `env: node: No such file or directory`。但奇怪的是，在终端（iTerm / Terminal）里一切又都是正常的。

## 0x01 问题现象

最近在 Marvis 里面配 MCP 服务器，发现只要调用 Homebrew 安装的 `npx`、`node`、`brew` 等命令就会报错：

Bash

```
command not found: npx
env: node: No such file or directory
```

但打开 iTerm2，敲同样的命令明明运行得好好的。

**经典的玄学时刻**：为什么同一个系统、同一个账户，终端里随便用的命令，放到 GUI 程序里就“查无此人”了？

## 0x02 排查与“抓包”过程

既然有问题，那就直接在 Marvis 的 shell 执行环境中敲命令排查，看看它的环境到底是啥样。

### 1. 看看 Marvis 到底拿到了什么 PATH

在 Marvis 内部直接执行：

Bash

```
echo "$PATH"
```

输出如下：

```
/Users/greenhandzdl/Library/Application Support/com.tencent.mac.marvis/components/MarvisAgent/Versions/1.0.0.10267/runtime/python311
/Users/greenhandzdl/Library/Application Support/com.tencent.mac.marvis/components/MarvisAgent/Versions/1.0.0.10267/runtime/python311/bin
/usr/bin:/bin:/usr/sbin:/sbin
```

**破案了**：Marvis 的 shell 环境极其干净，只有它自己自带的 Python 运行时目录 + 系统默认目录，**压根没有把 Homebrew 的路径（`/opt/homebrew/bin`）塞进来**。

### 2. 为什么终端有，它却没有？

跑个循环扫一下当前用户的各种 zsh / bash 配置文件：

Bash

```
for f in ~/.zshrc ~/.zprofile ~/.zshenv ~/.bashrc ~/.bash_profile ~/.profile /etc/zshenv /etc/zprofile /etc/zshrc; do echo "--- $f ---"; grep -n "PATH" "$f" 2>/dev/null; done
```

翻了一下输出：

- `~/.zprofile` 里面第一行写着 `eval "$(/opt/homebrew/bin/brew shellenv)"`（Homebrew 默认安装时写入的，这也是终端能用的原因）；
- `~/.zshrc` 里面加载了一堆变量（gcc、llvm、qt、fvm 等），但偏偏也没手动加过 `/opt/homebrew/bin`；
- `/etc/zprofile` 里只有系统的 `path_helper`，同样不带 Homebrew。

**原因**：Homebrew 路径是靠 `~/.zprofile` 在 zsh 启动时动态注入的。而普通的 GUI 程序启动时，根本不会去读这些 shell 配置文件。

### 3. 确认可执行文件位置

Bash

```
ls -l /opt/homebrew/bin/npx
ls -l /opt/homebrew/bin/node
/opt/homebrew/bin/npx -> ../Cellar/node/26.7.0/bin/npx
/opt/homebrew/bin/node -> ../Cellar/node/26.7.0/bin/node
```

软链接正常，文件都在，纯粹是因为程序“看不到”这个目录。

### 4. 看看全局 `launchctl` 环境

Bash

```
launchctl getenv PATH   # 拿出来是空的
```

### 5. 刨根问底：查看 Marvis 进程链和环境变量

Bash

```
ps -eo pid,ppid,lstart,command | grep -E "MarvisAgent|MarvisHost|MarvisService|MarvisGateway"
ps eww -p <pid> | tr ' ' '\n' | grep "^PATH="
```

扒了一下进程：

| **进程**                               | **看到的 PATH**                 |
| -------------------------------------- | ------------------------------- |
| Marvis 主进程                          | `/usr/bin:/bin:/usr/sbin:/sbin` |
| MarvisAgent（负责执行 shell 的子进程） | `/usr/bin:/bin:/usr/sbin:/sbin` |
| MarvisService（后台服务）              | `/usr/bin:/bin:/usr/sbin:/sbin` |

它的父进程链是这样的：

`bash -c` ← `MarvisAgent (PID 1526)` ← `Marvis 主进程 (PID 1489)`

而且每次 Marvis 调 shell 时，后台拼接的真实指令其实是：

Bash

```
bash -c '...; export PATH="<runtime>/python311:<runtime>/python311/bin:$PATH"'
```

也就是在系统默认 PATH 的基础上，硬编码贴上了它自己的内置 Python 环境，完全没把用户的全局 PATH 当回事。

### 6. 配置文件里能改吗？

把 Marvis 的各种配置翻了个遍：

- `~/Library/Application Support/com.tencent.mac.marvis/config.toml`
- `~/Library/Application Support/com.tencent.mac.marvis/marvis-client.config.json`
- `~/Library/LaunchAgents/com.tencent.mac.marvis.app.plist`

结论：**全都没有开放环境变量或 PATH 的配置入口**。LaunchAgent 里只简单粗暴地写了个 `open -a Marvis.app`。

### 7. 顺手试了下 `launchctl setenv`

Bash

```
launchctl setenv PATH "/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin"
```

重启 Marvis 后再测：`launchctl getenv PATH` 能看到值了，但在 Marvis 内部打印 `echo "$PATH"` 依然是老样子。因为通过 `open` 命令启动的子进程，根本没有继承到这个值。

## 0x03 搞懂本质：根因分析

1. **macOS 的“GUI ≠ 终端”硬伤**：通过 LaunchAgent 或 `open` 启动的 GUI 应用，默认继承的是 launchd Aqua 会话的最低环境变量（只有 `/usr/bin:/bin:/usr/sbin:/sbin`），它们根本不走 zsh，不会去读 `~/.zshrc` 或 `~/.zprofile`。
2. **`launchctl setenv` 不靠谱**：它只对 launchd 后面直接拉起的进程生效，对 `open -a` 启动的 App 或已经常驻后台的 daemon 完全不起作用。
3. **`npx` 的“双重依赖”陷阱**：就算你把 `npx` 的路径写死成 `/opt/homebrew/bin/npx`，它的脚本头（Shebang）依然写着 `#!/usr/bin/env node`。当它运行时，会**再次去 PATH 里找 node**。如果 PATH 还是缺的，就会触发 `env: node: No such file or directory`。所以光找到 `npx` 没用，必须让 `node` 也在 PATH 里。

## 0x04 解决方案

### 方案 A：改框架/全局配置（失败）

修改 Marvis 内部源码不现实，升级就覆盖；全局环境变量注入也基本死路一条。

**策略调整：不要试图去改变应用的启动环境，而是在“单条命令”维度实现“自给自足”。**

### 方案 B：zsh 脚本包装启动（最佳实践 🌟）

在配置 MCP 服务器或者执行命令时，不要直接调 `npx`，而是套一层 `zsh -c`：**先补充 PATH，再用 `exec` 替换进程**。

JSON

```
{
  "type": "stdio",
  "command": "/bin/zsh",
  "args": ["-c", "export PATH=/opt/homebrew/bin:/usr/local/bin:$PATH; exec npx -y <包名>"]
}
```

**细节点解析**：

- `/bin/zsh`：系统绝对路径，不需要依赖任何 PATH 解析，任何环境下肯定能调起来；
- `-c`：直接执行传入的字符串命令；
- `export PATH=...`：强行把 Apple Silicon (`/opt/homebrew/bin`) 和 Intel (`/usr/local/bin`) 的 Homebrew 路径挂到最前面，同时保留原有的 `$PATH`（避免破坏 Marvis 自己的 Python 环境）；
- `exec npx ...`：这里的 `exec` 很关键，它会让 `npx` 直接替换掉当前的 `zsh` 进程，减少不必要的进程嵌套，保证进程树干净；`-y` 则是让 npx 自动同意下载未安装的包。

**测试**：配置完后，`@vkhanhqui/figma-mcp-go` 顺利连上，58 个 tool 瞬间加载出来。

### 方案 C：绝对路径（仅限二进制）

如果调用的不是 Node/Python 这类依赖环境的脚本，而是独立的二进制工具，直接写死绝对路径即可：

JSON

```
{
  "type": "stdio",
  "command": "/opt/homebrew/bin/<可执行文件名称>"
}
```

### 方案 D：终端提前验证

在把配置塞进 MCP 之前，可以在终端里用下面这条命令“模拟小黑屋环境”测试一下能不能正常跑：

Bash

```
/bin/zsh -c 'export PATH=/opt/homebrew/bin:/usr/local/bin:$PATH; npx -y <包名>' </dev/null
```

*（加 `</dev/null` 是因为 macOS 没有 `timeout` 命令，这样可以让它读不到输入直接打印握手日志，方便观察是否报错）*

## 0x05 踩坑总结与排查 Checklist

如果你在其他的 macOS GUI 程序（比如 Raycast、VS Code 内嵌终端、各类 AI 客户端）里也碰到了“终端能跑，GUI 跑不通”的问题，可以按这个流程过一遍：

1. **查真实 PATH**：先别急着改配置，在程序内部把 `echo "$PATH"` 打出来，看看究竟缺了啥。
2. **放弃 `launchctl setenv`**：在 macOS 新版本上这玩意对绝大多数 `open` 启动的 GUI App 都不奏效，别在这浪费时间。
3. **改启动器而不是改 App**：如果是你自己写的 LaunchAgent plist，记得在 plist 里加上 `<key>EnvironmentVariables</key>`；如果只是用现成的 App，请直接使用 **`zsh -c 'export PATH=...; exec ...'`** 命令包装法。
4. **记住 `exec` 和绝对路径**：包装命令时，入口解释器（`/bin/zsh` 或 `/bin/bash`）务必使用绝对路径，调用的最终命令前面加上 `exec`。

有了这个包装模板，基本上所有 macOS 下 GUI 应用的环境变量缺失问题都能迎刃而解了。
