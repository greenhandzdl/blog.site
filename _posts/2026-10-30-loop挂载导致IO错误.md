# Docker 挂了但不是镜像的锅：一次 loop 挂载 I/O error 的 SELinux 标签定案

> **设备**：OnePlus Ace 3 Pro（`PJX110` / SM8650）· crDroid 16 · GKI 6.1（Floran Kernel，ReSukiSU + SUSFS） **相关组件**：模块 [`mgksu/dockerd`](https://github.com/mgksu/dockerd) + 自维护的 [`magisk-docker-fix`](https://github.com/greenhandzdl/magisk-docker-fix)

前几天 Docker 毫无征兆地原地去世了。`docker images` 连不上守护进程，`/proc/mounts` 里 data-root 的挂载点空空如也，模块日志直接一句“挂载失败，禁用模块”把路封死。

手动排查时，偏偏遇到了这么个诡异的现象：`losetup` 绑 loop 设备顺畅无比，但只要一执行 `mount`，立刻报 `I/O error`，`dmesg` 里还甩出两行 `Buffer I/O error on dev loop42, logical block 0, async page read`。

当时第一反应：完蛋，镜像文件怕不是哪块读不出磁道、彻底坏了。

结果折腾了一圈排下来，根本不是那么回事——**镜像好得很、空间也没满，纯粹是 `docker-data.img` 的 SELinux 标签被 `restorecon` 悄悄改回了 `adb_data_file`。而 loop 设备的内核预读（kworker）以 `u:r:kernel:s0` 身份去读它时惨遭拒签，预读直接崩成 EIO，ext4 拿不到 superblock，自然就挂载失败了。**

顺带还排查掉了两个假坑（loop 设备号其实没位移、镜像大小也没超限），顺手修掉了 `mount -o context=` 在当前 ROM 上必翻车的老 bug。记录一下整个定案过程。

## 1. 误判链：把“文件系统问题”逐个排除

### 1.1 镜像本身健康

```bash
e2fsck -fn /data/adb/docker-data.img
# 550731/4000000 inodes, 4218491/13107200 blocks (16.1G used), 0.1% non-contiguous
```

`dd` 直接读文件任意位置都正常（buffered，400MB/s），丢 cache 后重读也正常。ext4 文件系统本身是干净的，只有一次 journal replay。

### 1.2 不是稀疏文件

这台机器历史上真的踩过“F2FS + loop 读稀疏文件 EIO”的坑，先拿老经验过一遍：

```bash
stat -c '%b %B %s' /data/adb/docker-data.img
# blocks * blocksize == apparent size  → 全量分配，非稀疏
```

50G 全量落盘，排除。

### 1.3 核心分水岭：“换个目录”暴露出真实嫌疑

经过多轮递进实验，唯独一组操作出现了差异：**同样的文件内容、同样的命令，放在 `/data/local/tmp` 能挂，放在 `/data/adb` 就报 EIO**。

这把嫌疑从“文件/尺寸/空间”直接推到了“路径属性”上。

> 回头看，当时“把前 1G 复制到 `/data/local/tmp` 就能读”其实是个误导性证据——它能读不是因为 1G 比较小，而是因为它换了个目录、换了个 SELinux 类型（`shell_data_file`）。变量没控干净，方向差点跑偏。

### 1.4 工具小坑：loop 设备号“错位”的假象

中途误以为节点与内核设备号不一致：

```bash
stat -c %t:%T /dev/block/loop42   → 7:150
cat /sys/block/loop42/dev         → 7:336
```

查证后发现 `**stat -c %t:%T**` **输出的是十六进制**（`0x150 == 336`），节点和 sysfs 完全一致。*记一笔：看 dev_t 直接看 `ls -l` 的十进制，或者用 `stat -c '%D'`，别拿 `%t/%T` 当十进制读。*

## 2. 决定性证据：不是 I/O，是 SELinux 拒绝

翻看 `dmesg` 往上两行，真相就摆在那：

```text
avc: denied { read } for comm="kworker/u16:3" path="/data/adb/docker-data.img"
     dev="dm-52" ino=3630276
     scontext=u:r:kernel:s0
     tcontext=u:object_r:adb_data_file:s0
     tclass=file permissive=0

Buffer I/O error on dev loop42, logical block 0, async page read
```

逻辑链路非常清晰：

1. `losetup` 把文件挂到一个 loop 设备上（只做绑定，不读内容）；
2. ext4 mount 要读 superblock（offset 1024），块层先做**异步预读（readahead）**；
3. 预读不走 mount 进程上下文，而是丢给 `kworker`，域是 `**u:r:kernel:s0**`；
4. 文件类型是 `adb_data_file`，kernel 域对它**没有 `read` 权限**；
5. 预读失败被转译为块层 I/O 错误 → `Buffer I/O error ... logical block 0`；
6. ext4 判定 superblock 读不出来 → `unable to read superblock` → mount 返回 EIO。

简而言之：**同步的 `dd` 是 mount 进程（`ksu` 域）在读，允许；异步预读是 `kernel` 域在读，被拒。** 这完美解释了“文件好好的、buffered 读没问题、loop 就是 EIO”的全部矛盾。

### 单变量对照测试

同一份 `mke2fs` 出来的 16M ext4，只改标签后测试：

- `adb_data_file` / `system_data_file` ➔ ❌ I/O error
- `magisk_file` / `shell_data_file` ➔ ✅ 挂载成功

## 3. 为什么最近才频繁中招？

`/data/adb` 下新建文件的默认类型就是 `adb_data_file`。当触发以下操作时，会执行 `restorecon`：

- 手动 `restorecon -R /data/adb`（debug 开机慢时最容易顺手敲一发）；
- 刷 ROM / OTA 后 init 阶段的递归恢复；
- 各种优化脚本。

**标签一旦掉回 `adb_data_file`，下一次开机 Docker 必挂**，且由于失败路径会自动 `touch dockerd/disable`，导致后续连手动重试的机会都没有了。

## 4. 附带修复：避开 `mount -o context=` 的坑

旧脚本的挂载参数中带有转义双引号的 `context=` 选项：

```bash
mount -t ext4 -o "noatime,nodiratime,context=\"u:object_r:adb_data_file:s0\"" $DEV $ROOT
```

实测在本 ROM 上会直接报错：

```text
mount: ... Permission denied
```

且 `dmesg` 中没有任何 avc 报错（不是 SELinux 拒的，而是 mount 的选项处理有问题）。最佳实践是**放弃 `mount -o context=`，改用普通挂载 + 将标签直接写入镜像内部 xattr**：

```bash
mount -t ext4 -o noatime,nodiratime $DEV $ROOT
restorecon -R $ROOT      # 一次性，将标签固化进 ext4 内部
```

## 5. 模块层面（magisk-docker-fix v1.3）的改进

针对上述问题，在模块中作了针对性加固（commit `9130a34`）：

1. **强制纠偏**：所有挂载脚本在执行 `losetup` 前，统一执行 `chcon u:object_r:magisk_file:s0 $IMG`。
2. **移除 `context=`**，回归标准 ext4 挂载参数。
3. **保留现场**：挂载失败不再盲目 `2>/dev/null` 吞掉错误，确保 stderr 写入日志。
4. **幂等自检**：新增 `fix_inner_labels()`，仅在镜像内部标签为 `unlabeled` 时才在后台跑 `restorecon`，正常路径零额外开销。

核心逻辑 diff 示例：

```diff
 do_mount() {
+    # kernel 域无权读 adb_data_file，loop 预读 EIO -> ext4 读不到 superblock
+    chcon u:object_r:magisk_file:s0 $IMG 2>/dev/null
     DEV=$(losetup -f 2>/dev/null)
     ...
-    mount -t ext4 -o "noatime,nodiratime,context=\"u:object_r:adb_data_file:s0\"" $DEV $ROOT 2>/dev/null
+    if ! mount -t ext4 -o "noatime,nodiratime" $DEV $ROOT 2>>$LOG; then
         losetup -d $DEV 2>/dev/null
         return 1
     fi
```

## 6. 经验小结

1. `**Buffer I/O error**` **不一定是硬件或文件坏了**：优先检查 `dmesg` 有无 `avc: denied`，loop 预读跑在 `u:r:kernel:s0`，和 shell 里的 `dd` 不是一回事。
2. **“能 `dd` 读、不能 loop 读”** 是典型的 SELinux 异步预读权限拦截特征。
3. **善用目录对照**：换个目录测试（如 `/data/local/tmp`）能快速剥离文件本身的嫌疑。
4. `**2>/dev/null**` **是排障杀手**：关键错误日志千万不要无脑吞掉。
5. **别把故障直接和“开机变慢”划等号**：排查完发现挂载阶段耗时极短（t≈8s），开机慢往往源于其他遗留的轮询脚本。
